<h2>03 / 我的工程关注点</h2>
<details>
<summary>接口成功，不等于业务完成。</summary>
<p>请求受理、渠道处理成功、资金到账和对账完成，是不同的业务状态。设计接口时需要分别说明状态来源，以及超时、重试和重复通知时怎么处理。</p>
</details>

<details>
<summary>先说清边界，再谈怎么实现。</summary>
<p>跨系统协作先确定责任边界：谁发起请求，谁持有最终状态，重复调用如何识别，异常由谁处理。边界不清楚，增加重试次数也不能解决问题。</p>
</details>

<details>
<summary>问题要能沿着链路查回去。</summary>
<p>排查一笔异常时，需要把入口请求、业务单号、外部响应和状态变更放在同一条时间线上。记录应足够定位问题，也要避免把敏感数据直接写入日志。</p>
</details>

<h2>04 / 我怎么看 AI 的下一步。</h2>
<p class="ai-lead">我判断，AI 会继续从回答问题走向执行任务。工程师的价值，也会更多落在定义目标、搭好运行环境和验收结果上。</p>
<div class="ai-principles"><article class="ai-principle"><p class="ai-label"><span>01</span> DEFINE THE OUTCOME</p><h3>把目标提一层。</h3><p>我不只问 AI 能帮我完成哪一步，还会问：做完之后，我真正希望改变什么。执行成本下降后，更值得把时间花在选对问题上。</p></article><article class="ai-principle"><p class="ai-label"><span>02</span> BUILD THE HARNESS</p><h3>给它工具，也给它边界。</h3><p>模型只是其中一层。能干活的 Agent 还需要数据、工具、记忆和运行环境。权限、人工审批、沙箱和可观测性，要和能力一起设计。</p><a class="ai-reference" href="https://interview.sageflow.online/#/doc/d123" target="_blank" rel="noopener noreferrer">阅读运行时安全研究 ↗</a></article><article class="ai-principle"><p class="ai-label"><span>03</span> VERIFY OUTSIDE THE MODEL</p><h3>结果要经得起外部验证。</h3><p>AI 自己说完成了，不算验收。我要看测试、故障实验和可复现的结果。成本、延迟与已知限制，也要说清楚。</p><a class="ai-reference" href="https://interview.sageflow.online/#/doc/d55" target="_blank" rel="noopener noreferrer">阅读评测与可观测性专题 ↗</a></article><article class="ai-principle"><p class="ai-label"><span>04</span> WORK WITH REAL CONSTRAINTS</p><h3>在现实约束里寻找机会。</h3><p>国内和海外的模型可用性、成本与数据要求并不一样。我更关注按任务选模型、云端与本地协作，以及把 AI 接进具体业务，而不是只追榜单。</p></article></div>
